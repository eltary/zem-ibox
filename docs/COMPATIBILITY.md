# Совместимость и возможности

Исследован предоставленный оригинальный DVRunning2 в `research/decompiled/`.
Это семейство камер Jieli с CTP, а не универсальный протокол всех регистраторов.
Подтверждён пользователем iBOX Flash WiFi Dual, описание
`AC54xx_wifi_car_camera`, прошивка 1.0.1. Других физических моделей для
проверки сейчас нет; список совместимых брендов из одного имени чипа не выводится.

## Как определяется устройство

- CTP TCP 3333; описание `/mnt/spiflash/res/dev_desc.txt` по HTTP 8080.
- `net_type=0` — собственный TCP поток 2229 с 20-байтовым заголовком.
  `net_type=1` — UDP 2224 спереди / 2225 сзади; перестановка фрагментов допустима.
- `rts_type=0` — MJPEG, `1` — H264. Это формат потока, не число камер.
- `forward_support` / `behind_support` — уровни качества соответствующего
  потока. Они не подтверждают физическое наличие задней камеры.
- Оригинал проверяет `PULL_VIDEO_STATUS.status`. На iBOX пользователя без
  второй камеры прошивка всё равно присылает 1, поэтому Zem iBox дополнительно
  требует включить её в настройках профиля. Ответ 0 и ошибки 15/16 скрывают
  выбор и возвращают на переднюю.
- Профиль привязан к UUID + типу устройства, с резервом SSID / локальный IP.
  Смена IP при наличии UUID не создаёт другой профиль.
- `errno=6` означает неподдерживаемую команду; настройки без полученного
  значения или без нужного ключа не показываются. Модель/SSID берётся из камеры.

Источники в оригинале: `bean/DeviceDesc.java`, `util/AppUtils.java`
(разбор описания, строки около 940–1100), `util/IConstant.java` (порты и поля),
`ui/fragment/VideoFragment.java` (PULL_VIDEO_STATUS, около 846–879),
`ui/fragment/settings/RecordQualityFragment.java`, `res/values/arrays.xml`.
Пути источников Java относительны
`research/decompiled/sources/com/jieli/stream/dv/running2/`.

| Снимок и запись просмотра на телефон | JPEG и MP4; для MJPEG выполняется перекодирование, RTSP/H264 может сохраняться в MKV |
| Архив, обычные/закреплённые ролики, фото | Поиск, просмотр, скачивание папки от новых к старым |
| Скачивание оригиналов | Очередь, Range-продолжение, пропуск полных дублей, отдельные папки защиты |
| Проигрывание по Wi-Fi | Встроенный libVLC: MOV/MP4/AVI, предыдущий/следующий/список, 0,25×–4×; TextureView, совместимый режим, ограниченные Range-чтения; без привязки процесса |
| Превью файлов | Кэшированные кадры MOV/MP4, AVI/MJPEG и фото; проверено на симуляторе, зависят от контейнера и HTTP Range |
| Галерея телефона | Превью, системный выбор плеера/галереи, обмен файлами и отдельный режим просмотра видео подряд |
| Настройки CTP | Полученные значения: звук, экспозиция, язык, циклическая запись и др.; состав зависит от прошивки |
| Диагностика | Короткий отчёт одним сообщением, полный журнал файлом, очистка, постоянный переключатель записи |
| Форматирование microSD | По отдельному подтверждению, с остановкой записи и проверкой FORMAT.frm=1 |

| OTA/FTP прошивки, GPS/карты, двусторонняя речь, проекция | Обнаруженные отдельные возможности оригинала; сейчас не реализованы |

Оригинал также читает `forward_record_support`, `behind_record_support`,
`rtsp_forward_support`, `rtsp_behind_support`, `support_bumping`,
`support_projection`, `ota_type`, `ota_step`. Это описательные возможности
конкретной прошивки. Наличие поля не означает проверенную реализацию Zem iBox.
Оригинальный интерфейс содержит подписи 2K/4K, но исследованный
`getRtsResolution()` реально сопоставляет только VGA/720p/1080p; переносить
такие подписи как обещание 4K нельзя.

RTSP URL в оригинале — `rtsp://<IP>:554/264_pcm_rt/XXX.sd|hd|fhd`
(передняя H264), `rear.sd|hd|fhd` (задняя), либо
`avi_pcm_rt/front.sd|hd|fhd` / `rear.sd|hd|fhd` для MJPEG.
Собственный TCP 2229 нельзя просто передать VLC как обычный RTSP URL:
необходимо разбирать транспортные заголовки. TCP/UDP лайв использует MediaCodec,
RTSP и файлы архива — libVLC. В настройках регистратора можно выбрать
«Автоматически», TCP, UDP или RTSP. Выбор сохраняется в профиле устройства.
Автоматический режим использует net_type, а при его отсутствии — объявленную
поддержку RTSP либо UDP. Строковые JSON-массивы возможностей также поддерживаются.

RTSP сначала использует RTP поверх TCP через отдельный loopback-мост.
Если камера отклоняет TCP ответом RTSP 461, выполняется одна попытка UDP: мост
согласует client_port/server_port, принимает RTP/RTCP на Wi-Fi и передаёт native
плееру interleaved-пакеты. Обратный RTCP также отправляется через Wi-Fi.
Произвольные повторы подключения не создаются.
Все соединения с камерой создаются через захваченный Android Network Wi-Fi;
процесс и остальные приложения к этой сети не привязываются. Параметры SDP и
адреса управляющих треков переводятся мостом на тот же хост камеры. Для H.264
запись сохраняет контейнер, выбранный native muxer (например MKV); для MJPEG
восстанавливаются JPEG-кадры RTP и PCM 8 кГц mono, затем записывается MP4/H.264/AAC.
Файлы RTSP могут иметь расширение MKV вместо MP4. Неизвестные варианты аудио
и нестандартные типы RTP/JPEG нельзя считать проверенными.

Для новой модели нужны её описание, ответы CTP и реальная проверка просмотра,
звука, архива и записи. Автотест симулятора проверяет протокол и приложение,
но не заменяет испытание конкретной камеры и телефона.

## Проверка просмотра 25.10.2026

На Samsung SM-S938B / Android 16 пользователь сообщил о чёрном экране
архивного MOV в 0.0.10 при идущем таймере. Журнал содержит ошибку VLC
`cannot seek (to offset 148500000)` и серию SocketException; класс исключения
без сообщения не позволяет установить причину каждого завершения запроса.
Закрытие HTTP-сокета также нормально при отмене запроса или перемотке.

В 0.0.11 изменены вывод кадров, режим декодирования и Wi-Fi relay.
Синтетический Full HD MOV / 60 с / 138 МБ проверяет большой файл с индексом
в конце, перемотку и видимые кадры. Это не оригинальный файл с регистратора;
подтверждение исправления на физическом Samsung/iBOX пока ожидается.
Подробности — [отчёт проверки](PLAYBACK-0.0.11.md).

## Проверка по журналу 03.11.2026

В 0.0.11 архив на Samsung/iBOX продолжал стоять на 0%: `no moov before mdat and the stream is not seekable`.
Relay считал сервер неперематываемым по HTTP 200 на `bytes=0-0`; такой ответ
не доказывает отсутствие поддержки ненулевых смещений. В 0.0.12 добавлена
отдельная проверка `bytes=1-1`, ограниченное чтение нулевого ответа 200 и
понятное завершение ожидания вместо бесконечной загрузки.

Журнал также показывает пачки кадров лайва при нулевых счётчиках потерь
приложения. В 0.0.12 показ использует временные метки и небольшой буфер;
запись больше не использует время выполнения асинхронной задачи.
Изменения проверяются на симуляторе, включая пакетный приём, временные метки MP4
и реальный вывод декодера. Плавность на физическом iBOX/Samsung ещё требует
подтверждения. Долгие сетевые паузы буфер восстановить не может.

Пункты «Внутренний плеер» и «Открыть через VLC» разделены. Внутренний движок
по-прежнему libVLC 3.7.7, внешний VLC устанавливается отдельно. Во внешнем VLC
чтение архива также идёт через Wi-Fi relay, пока экран Zem iBox остаётся в стеке.

## Изменения 0.0.13 по отчёту Samsung/iBOX

Воспроизведён зависший на 250 мс native clock локального видео без аудио.
Для дескриптора с нулевым смещением теперь используется обычный FileDescriptor;
AssetFileDescriptor сохраняется для источников с ненулевым смещением. Таймер
не подменяется временем интерфейса. Портретный вывод рассчитывается по границам
видео, а не ориентации всего телефона: полный кадр помещается в область просмотра.

Во время лайва фоновые чтения превью архива приостановлены. Если активная запись
регистратора сообщает совпадающие камеру/размер и частоту кадров VIDEO_FINISH.p,
она уточняет частоту потока; SPS VUI имеет более высокий приоритет. Это устраняет
два источника неравномерности, но не доказывает отсутствие сетевых пауз на устройстве.

Совместимость расширена на найденные в исследованном DVRunning2 варианты транспорта
и кодеков. Это не обещание проверки всех продаваемых моделей и не полный перенос
OTA, GPS, проекции или двусторонней речи. Реальная проверка новых моделей остаётся
необходимой. Подробности — [проверка 0.0.13](PLAYBACK-0.0.13.md).
